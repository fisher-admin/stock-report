# 选股系统架构诊断与改造方案（2026-10-30）

作者：Claude Code（Mac）｜依据：Hermes 运行输出 2026-08-17 ～ 2026-10-29、各次事故日记、现网代码

## 一、结论先行

近两个月的故障看上去五花八门，但都出自六个架构缺陷。逐个修 bug 只能消掉“这一次”的症状，同类问题会换个位置再冒出来。要根治，得把这六处结构改掉。

| # | 架构缺陷 | 近期症状（举例） |
|---|---|---|
| 1 | 生产跑在一台“共享、无防护”的个人电脑上 | 10-20 Codex 清理删掉 AI 解释器，停 3 天；10-25/26 视频渲染吃满内存导致内核崩溃、当日任务晚点数小时；磁盘 95%；10-29 git fetch 网络失败 |
| 2 | 同一份数据被多个任务在不同时刻各自抓取 | daily_basic 由 22:15 研究、次日 08:15 事件漂移分别抓取：研究一超时，前瞻影子 10-26～29 连丢 4 天；08:15 接口一挂，事件漂移就失败（10-29）；两次抓取不一致又让短线研究失败（10-01、10-20） |
| 3 | 按固定钟点串起来的任务链，依赖关系靠“猜文件” | 19:30 一挂，20:00/21:05/22:15/23:30/次日 08:00/08:15/12:00 全部跟着报错；主机晚点就整链错位 |

| 5 | 生产与研究强耦合 | 前瞻影子（生产观察）依赖研究任务的副产物；研究失败直接造成生产观察数据永久缺口 |
| 6 | 生产配置不受控，多个代理直接改生产 | `~/.hermes/scripts/stock/*.sh` 包装脚本不在版本控制里，多会话各自改动；workspace 即生产，没有发布前的验证环节 |

## 二、目标架构

```
            ┌──────────── 运行环境（隔离、常在线）────────────┐
 外部数据 ─▶│ ① 数据层：每交易日一次入库 → 不可变按日存储       │
 (RDS/Promax)│      ↓ 只读                                      │
            │ ② 调度层：按交易日的依赖图（就绪即跑、失败重试、漏日补跑）│
            │      ↓                                           │
            │ ③ 计算层：生产选股 │ 生产观察（影子） │ 研究（可失败） │
            │      ↓                                           │
            │ ④ 发布层：网页 / Discord（单一根因告警）           │
            └──────────────────────────────────────────────────┘
```

原则：
1. **外部接口只在数据层出现**。下游一律只读本地冻结数据，接口故障只影响“入库”这一处，并且可以重试、补抓。
2. **每天每份数据只抓一次、只冻结一次**。“先写者为准”，事后修订单独留痕，不覆盖。
3. **依赖靠“数据就绪”驱动，不靠钟点**。每一步声明自己需要哪些输入，输入齐了才跑；没齐就等，等到超时再报一条根因告警。
4. **研究失败不得影响生产观察**。研究只读数据层，不给别人生产数据。
5. **增量计算**。历史只算一次，每晚只处理新的一天。
6. **生产代码与配置全部纳入版本控制**，改动先验证再上线。

## 三、分阶段实施

### 第 1 阶段（已完成，2026-10-30，commit f57430e）：数据层统一冻结
- stage1（19:30 数据准备）在当日行情就绪后，抓取并冻结当日 PIT 快照（universe + daily_basic）到共享库 `fundamental_cache/pit_market/v2`。已冻结的不重抓；失败只记录，不阻断选股。
- 短线研究、事件漂移改为优先读冻结版本，缺失时才调接口。
- 前瞻影子把共享冻结库放在首位，不再依赖 22:15 研究任务（规格哈希不变）。
- 此前已完成（10-23）：漏日自动补数、16:30 预检、21:20 自动补跑、晨判/午盘降级。

### 第 2 阶段（验证完成，待批准上线；见 stock-system-phase2-validation-2026-10-30.md）：研究计算增量化
- 短线研究不再每晚重抓 21 天。做法是把按日缓存的前复权数据按“复权因子之比”重新换算到新基准：价格和 MACD 都是线性量，换算是精确的。每晚只需抓 1 天。
- 需要先用历史数据验证：换算结果与供应商当晚口径逐位一致（或在可接受误差内），再上线。这会影响研究口径，上线前请你确认。

### 第 3 阶段（需要你决定）：调度从“固定钟点链”改为“按交易日的依赖图”
- 用一个轻量的状态机/依赖图执行器（自写约 300 行，或用现成工具），按交易日维护每一步的状态（待运行/运行中/成功/失败/跳过）。
- Hermes 只负责每隔几分钟唤醒一次执行器，执行器判断哪些步骤输入已就绪就去跑。
- 结果：上游晚点，下游自动顺延；上游失败，下游统一标“因上游跳过”，只发一条根因告警；漏掉的日子自动排队补跑。
- 风险：要改动全部 12 个 Hermes 任务的运作方式，建议先并行试运行一周再切换。

### 第 4 阶段（需要你决定，可能涉及花费）：运行环境隔离
- 方案 A（推荐）：一台常在线的专用小主机（如 Mac mini），只跑股票系统，不装其他会大量吃资源的项目。成本是一次性硬件投入。
- 方案 B：仍用这台 Mac，但给股票系统单独开一个 macOS 用户，用资源限制和目录权限隔离，并保持不休眠。零成本，隔离程度中等。
- 方案 C：云主机。要考虑数据接口白名单与网络访问。
- 无论选哪种，都应：纳管 `~/.hermes/scripts/stock` 包装脚本（版本控制 + 一键部署）；磁盘余量常备 20 GB 以上。

### 第 5 阶段：可观测性
- 每个交易日一张“运行状态卡”，覆盖每一步的输入就绪时刻、耗时、结果和根因。
- Discord 只推两类消息：根因告警（每次事故一条）和恢复通知。

## 四、需要你决定的事项

1. 是否开始第 2 阶段（研究增量化，会影响研究口径，需要先做对齐验证）。
2. 第 3 阶段调度改造：自写执行器还是引入现成工具；能否接受先并行试运行一周。
3. 第 4 阶段运行环境选 A、B 还是 C。

### 第 4 阶段：Docker 容器方案（fisher 选定：不新增设备，用本机 Docker）
**试点结论：可行**（commit f865d1b，`ops/container/`）
- 主环境 141 个依赖在 linux/arm64 镜像中全部可装（镜像 1.87 GB）。
- 工作区按原路径挂进容器（110 个文件写死了 `/Users/fisher/...`，同路径挂载无需改代码；必须用 `--mount`，`-v` 会被镜像内同名空目录遮住）。
- 核心单测 103 个中 100 个通过；3 个失败暴露了平台耦合（外部 `kill` 命令已修复；包装脚本在 `~/.hermes` 不在仓库里，需纳管）。
- 真实接口端到端：增量取数结果与本机一致，前 20 名一致，139 秒，内存峰值 510 MB。
- 凭据：`.secrets/` 可只读读取；需设置 `OPENCLAW_WORKSPACE_DIR` 等环境变量，否则会按容器家目录 `/root` 去找。

**三个硬约束**
1. **磁盘**：把生产数据（约 15 GB：stock_data 9.1 GB、factor_factory/data 5.3 GB 等）迁入 Docker 数据卷，迁移时需要同等的临时空间。Docker 的磁盘镜像也在这块盘上，并不增加容量。当前只剩约 13 GB，需要先腾出 ≥ 20 GB。
2. **Docker 本身也可能被清掉**：`~/Library/Containers/com.docker.docker`（8.6 GB）在磁盘清理工具眼里很“诱人”，Docker Desktop 的“清除数据”也会抹掉所有数据卷。因此必须每晚把数据卷备份到 Docker 之外，并在各代理的清理规则里明确排除。
3. **同一台机器**：内核崩溃、睡眠仍会影响容器。容器能隔离的是文件、依赖、内存上限，隔离不了主机本身。Docker 虚拟机目前只分配了 5 GB 内存，较重的研究任务内存峰值还没实测，可能需要调到 8 GB。

**分步迁移**
- **A（不需要腾空间，可立即开始）**：所有任务改在镜像里运行（三套 Python 环境：主环境 3.14、AI 3.11、qlib 3.9），包装脚本与执行器纳入仓库，Hermes 只负责 `docker run`；数据仍在本机，按原路径挂载。效果：解释器和依赖再也不会被主机清理删掉（10-20 类故障）；环境可由仓库一键重建。先和现有运行并行对照，再切换。
- **B（腾出 ≥ 20 GB 后）**：生产数据迁入数据卷 `stock-data`，主机上不再保留可写副本；研究会话通过容器或只读导出访问。每晚把数据卷快照备份到主机备份目录。效果：主机侧误删（rm -rf、清理工具）碰不到生产数据。
- **C（加固）**：Docker 开机自启并纳入 16:30 预检；数据卷备份校验；在 AGENTS.md / 各代理规则中写明禁止清理的路径。

**A 的进展（10-30 14:45）：运行镜像已建成**（fisher 决定不再腾空间，在现有余量内完成；B 因空间暂不做）
- 三个叠加镜像：`Dockerfile`（主环境）→ `Dockerfile.ai` → `Dockerfile.qlib`，最终 `stock-runtime:latest` 4.55 GB。每步一层、不装编译器，全部用预编译包。
- `ops/container/build.sh`：构建前要求余量 ≥ 10 GB + 预估；构建中余量跌破 10 GB 即中止；每步完成后清构建缓存（吸取 10-30 磁盘写满教训）。
- `ops/container/run.sh`：工作区按原路径挂载；AI/qlib 环境用按镜像 ID 命名的数据卷覆盖；`~/.hermes` 只读；Copilot 令牌由宿主传入。
- 验证：三环境探针通过、Copilot 令牌可用、单测 649 个中仅 1 个失败（宿主同样失败，既有问题）。
